## 1. 目标与不变量

交付物（报告、工作簿、文档）不是"模型写出来的文件"，而是**确定性算力的投影**：
管线中每一个数字、每一条结论都出自 server 侧确定性服务（数值求值/单位推断/
推理状态机等，逐位可复算），渲染层只做无副作用的形状转换。

管线承诺四条不变量：

1. **零内置时钟**：template_render 禁内置时间/随机——时间等非确定量必须由
   调用方作为显式值放进 context；三个导出服务的文档属性时间戳固定写入，
   零时间戳内嵌。
2. **逐位可复算**：同一组服务调用序列 + 同一组入参 ⇒ 逐字节一致的交付物。
   渲染器为纯 Rust 实现（PDF 文本型渲染 / rust_xlsxwriter / docx-rs），
   不引入解释器层的浮动因素。
3. **溯源内嵌**：每个数字可回指其出处服务、入参、信封摘要（blake3 内容哈希）。
   xlsx 以溯源表为第一张工作表；docx 以溯源表节收尾；PDF 以元信息与完整性块
   呈现。
4. **幂等覆写**：同一逻辑交付物重复导出落同一路径，返回绝对路径、字节数与
   blake3 内容哈希——哈希即交付物指纹，二次导出哈希不变。

## 2. 管线架构

```
┌────────────────────────────────────────────────────────────────────┐
│  server 侧确定性算力层（numeric / inference 状态机族服务）            │
│  输入 → 确定性求值 → 结论 + 信封摘要（blake3）                       │
└──────────────┬─────────────────────────────────────────────────────┘
               │ 结论 + {service, args, digest} 溯源三元组
               ▼
┌────────────────────────────────────────────────────────────────────┐
│  形状装配层（template_render，确定性纯函数）                          │
│  {{}} 变量替换 + if/for 最小控制流 → JSON / Markdown / 纯文本         │
│  json 格式额外做合法性校验，不合法即报错                              │
└──────────────┬─────────────────────────────────────────────────────┘
               │ 渲染就绪的标题/段落/表格/溯源表
               ▼
┌────────────────────────────────────────────────────────────────────┐
│  导出层（export_report_pdf / export_workbook_xlsx /                  │
│          export_document_docx，纯 Rust 渲染器）                      │
│  落盘导出目录 → 返回 {绝对路径, 字节数, blake3 内容哈希}，幂等覆写     │
└────────────────────────────────────────────────────────────────────┘
```

agent（LLM）在管线中的职责只有**编排与叙述**：决定调用哪个服务、组织入参、
选择模板与导出格式。所有数值与判定都来自确定性服务；模型不手算数字进交付物，
也不生成渲染代码。

## 3. 服务契约速览

以下四件服务由 server 插件面（GET /api/services 对账清单）声明，agent 经
服务消费桥以同名代理工具直调（POST /api/services/{name}/invoke）：

| 服务 | 必填参数 | 关键可选参数 | 确定性要点 |
|---|---|---|---|
| `template_render` | `template` | `context`、`format`(text/markdown/json) | 纯函数；禁内置时钟/随机 |
| `export_report_pdf` | `content_type` | `business_data`、`raw_data`、`meta`、`integrity`、`options`、`filename` | 纯 Rust 文本型 PDF；零时间戳内嵌 |
| `export_workbook_xlsx` | `sheets` | `provenance`、`title`、`filename` | rust_xlsxwriter；固定文档时间戳；溯源表为首表 |
| `export_document_docx` | （对账清单未声明参数契约，schema 降级空 object） | — | docx-rs；零时间戳内嵌 |

> `export_document_docx` 的参数契约缺口是 server 侧插件声明面的事实：对账清单
> 未带 `parameters` 声明，agent 侧按既有语义如实降级空 object（不伪造契约）。
> 补齐该声明属 server 仓后续工作。

xlsx 的 `provenance` 数组每项四字段：`claim`（断言）、`service`（出处服务）、
`args`（入参压缩 JSON）、`digest`（信封摘要）——渲染为首张工作表，是
"可复算的交付物"的机器可读入口。

## 4. agent 侧接线

服务消费桥（`src/service_tools.rs`）是唯一执行路径：启动时经 GET /api/services
发现服务，按 `config.evorule.service_tools` 白名单注册同名代理工具；执行经
POST /api/services/{name}/invoke 直调（与 io_request 同一执行链，无第二实现）。

接线面四处：

1. **注册白名单**（`examples/config.toml` 的 `[evorule].service_tools`）：
   部署面把四件交付物服务列入推荐白名单；空白名单 = 不注册任何服务工具
   （安全默认不变）。注册语义：缺失服务跳过并点名、sensitive 服务跳过、
   与本地工具重名跳过（本地优先）。
2. **agent 声明面**（`agents/general.json`、`agents/tb-agent.json` 的 `tools`）：
   以尾缀通配条目 `export_*`、`template_*` 声明交付物工具族——与 `mcp_*` 同一
   既有机制（动态名工具的声明形态，存在性校验豁免，server 不可达时降级缺席
   不阻塞启动）。精确注册控制权始终在配置白名单：声明面表达"愿意用"，
   白名单表达"真的注册"，两层都过才有工具面。
3. **LLM 契约面**：runner 组装工具 schema 时，服务代理工具无静态 spec，从
   注册缓存透出对账清单的 description/parameters——模板渲染必填 `template`、
   报告导出必填 `content_type`、工作簿导出必填 `sheets`，模型带参直调。
4. **治理语义**：服务代理条目缺省绑定服务代理开关键（缺省开）；意图裁决分级
   与 MCP 动态源同款；结果超 100KB 按字符边界截断并在结果中注明原始字节数
   （交付物返回的是小回执——路径/字节数/哈希——远低于上限）。

## 5. xlsx/docx 生成方案结论

**结论：采用 server 侧既有确定性导出服务（export_workbook_xlsx /
export_document_docx），经服务消费桥接线；不新建 agent 侧生成工具，
不走 python_exec + openpyxl/python-docx 路线。**

理由：

1. **服务已存在**：server 的 export-services 插件已提供两件服务（确定性渲染、
   返回路径/字节数/blake3 哈希、幂等覆写），缺口只是 agent 侧接线——工作量
   从"新建生成能力"收敛为"白名单 + 声明面两处配置"。
2. **python_exec 路线违背管线不变量**：
   - LLM 现写代码 = 每次运行的代码文本都可能不同 ⇒ 不可复算；
   - 无统一回执形态（路径/字节数/哈希），溯源链断裂；
   - 引入 Python 依赖面（openpyxl/python-docx 版本漂移），交付物指纹随依赖
     版本浮动；server 侧纯 Rust 渲染器无此面。
   - python_exec 保留其既有定位（自由探查/胶水），但**不承担交付物生成**——
     交付物一律走确定性导出服务，哈希指纹才可对外承诺。
3. **文档时间戳可控**：xlsx 固定文档时间戳、docx 零时间戳内嵌——同内容双跑
   逐字节一致；openpyxl 默认写当前时间戳，需要调用方自行伪造时间字段才能
   对齐，属第二实现负担。

## 6. 可复算性叙事：一次交付的完整证据链

以"赛题结果报告"为例，一次交付的证据链：

1. **数字层**：结果数值由 numeric 族服务定点求值（十进制字符串值域，无浮点），
   判定结论由 inference 族状态机给出；每次调用返回结论 + blake3 信封摘要。
2. **装配层**：模板把结论与数字排进章节；模板变量取值全部来自上一步的服务
   回执（显式 context），无隐藏取值。
3. **导出层**：xlsx 第一张表 = 溯源表（claim/service/args/digest 逐行）；
   PDF 元信息块 = 会话标识/范围/规则集版本；docx 溯源表节同构。
4. **复算**：第三方拿到交付物后，按溯源表逐行重放服务调用（同服务/同入参），
   比对 digest 与交付物内嵌数字——一致则交付物成立。交付物文件本身的
   blake3 哈希是最终指纹：同序列重跑导出，指纹不变。

这条链的每一环都是确定性纯函数或幂等落盘，**没有一环依赖模型自报**——
模型只决定"算什么、排成什么形状"，不决定"数字是多少、文件里是什么字节"。

## 7. 边界与已知缺口

- `export_document_docx` 参数契约未在服务对账清单声明（agent 侧如实降级空
  schema）；补声明属 server 仓后续工作，agent 侧零改动自动受益。
- PDF 渲染为文本型（标题/段落/表格），不含图像排版；复杂版式需求候
  server 侧渲染器扩展，agent 侧契约不变。
- 服务清单为启动期发现快照：server 新增服务需重启 agent 进程面才会注册
  （运行期服务重载不在本管线范围）。
- 测试面：服务消费桥注册/契约缓存/直调透传、LLM schema 必填参数形态各有
  用例锁定（`src/service_tools.rs`、`src/agent/runner_tests.rs`）；agent 声明面
  白名单可解析性由 serve 工具面测试守护。
